# 检索评测 · 向量腿落地与架构修正报告（2026-09-28）

## 结论先行

引入真实 embedding 模型（BGE 中文小模型，本地离线向量化）后，**评测数据推翻了此前 LLM 增强管线的架构判断**——这是评测驱动开发最直接的证明：

| 方案 | Recall@1 | Recall@3 | MRR | 每查询成本 |
|---|---|---|---|---|
| ① 纯稀疏基线（TF-IDF bigram） | 0.392 | 0.590 | 0.511 | 0 |
| ② 稀疏+稠密 RRF 混合（零 LLM） | 0.669 | 0.904 | 0.785 | 0（本地向量 ~10ms） |
| ③ 增强管线（改写+RRF+LLM重排）* | 0.904 | 0.928 | 0.918 | 2 次 LLM |
| ④ 纯稠密（BGE bge-small-zh-v1.5） | 0.892 | 0.946 | 0.922 | 0（本地向量 ~10ms） |
| ⑤ 稠密 + LLM listwise 重排 | **0.982** | **0.982** | **0.982** | 1 次 LLM |

*③ 为 2026-09-18 评测结果（无稠密腿时的最优方案）。

## 三个评测发现（全部可复现）

**发现 1：强稠密模型让"查询改写"变得不必要（④ > ③）。**
此前词汇鸿沟靠 LLM 查询改写弥合（+23.5pp）；BGE 向量把语义直接编码进检索本身，零 LLM 成本就做到 Recall@3 0.946，超过花 2 次 LLM 的旧管线。**改写步是对"弱字面匹配"的补丁，有了强稠密模型补丁可以撕掉。**

**发现 2：RRF 融合不是万能的——弱腿拖累强腿（② < ④）。**
稀疏+稠密混合（0.904）反而低于纯稠密（0.946）：稀疏腿在部分查询上给出高置信的错误排序，RRF 按排名平均后把稠密腿的正确 top1 拉了下来。**融合的价值取决于各腿的相对强度：当稠密模型对语料覆盖充分时，融合弱稀疏腿损害头部精度。**（稀疏腿保留价值：embedding 服务故障时的降级路径 + 极端专有名词的精确匹配。）

**发现 3：稠密+重排逼近单标注上限（⑤ = 0.982）。**
Recall@1/3/5/MRR 全部相等，说明期望文档要么排第 1、要么彻底 miss——剩余 1.8%（3/166）是语义上真正无关联的改写查询，重排无法拯救召回层面就不存在的候选。

## 架构决策修正（评测 → 选型）

- **新检索主方案**：稠密召回（top8）→ LLM 重排（1 次调用）→ top3，替代旧"改写+双路RRF+重排"（2 次调用）——**成本减半，Recall@3 +5.4pp**；
- **稀疏腿降级为 fallback**：embedding 服务不可用时回退 TF-IDF（带降级 trace 标记）；
- **下一步（部署侧）**：云函数无法内嵌 30MB 模型（包体限制），embedding 服务拆分到 CloudRun 容器（FastAPI/Node + ONNX runtime），云函数经内网 HTTP 调用——这是把 ④⑤ 的离线结论落到生产路径的剩余工作。

## 实现说明

- 模型：`Xenova/bge-small-zh-v1.5`（ONNX q8 量化，512 维，cls pooling + 归一化），经 transformers.js 本地推理（hf-mirror 拉取），CPU 单条 ~3ms；
- 文档向量离线一次性构建：`node evals/embedDocs.js` → `evals/doc_vectors.json`（166×512，已入库便于评测离线复现）；查询向量实时编码；
- 评测模式：`node evals/retrieval_eval.js --vector-only | --hybrid | --dense-rerank`；
- 诚实限制：⑤ 依赖 hy3 重排（网关）；生产 embedding 服务未部署（本地 CPU 推理仅覆盖离线评测与后续 CloudRun 拆分的模型选型依据）；单标注黄金集的 0.982 仍可能低估真实召回。
